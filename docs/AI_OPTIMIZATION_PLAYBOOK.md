# AI 协作优化手册（提示词体系）

> 结论先说：让 AI 安全地优化这个项目，靠的不是"优化"这个词，而是
> **`AGENTS.md` 锁底线 + 任务提示词锁范围与验收 + 先方案后代码 + 小步验证**。
>
> - 长期不变的规范 → `AGENTS.md`（项目根目录，AI 每次对话自动读取）
> - 本次要改什么、改到什么程度、拿什么证明 → 复制下面的场景提示词到对话里
>
> 两者不要混在一起。规则文件里写"本次要改 Foo.py"，下一个人就被过期信息误导；
> 对话里重述一遍"注释要用中文"，就是在浪费一次说明。

---

## 一、两层约束怎么分工

| 层 | 放哪 | 内容 | 变化频率 |
|---|---|---|---|
| **规则层** | `AGENTS.md` | 技术栈、命令、架构红线、行为守恒铁律、异常处理写法、测试规范、提交与文档规范 | 随项目演进（季度级） |
| **任务层** | 对话 | 本次的目标、允许改的文件、必须保留的行为、验收标准、输出格式 | 每次任务 |

**为什么必须有规则层**：本仓库有几条"AI 不知道就一定会踩"的隐性约束 ——
板块之间不许互相 import、`services/app_context.py` 不是死代码、`# noqa: BLE001`
不能删、`ACTIVE_BOARDS` 顺序不能插队。这些内容每次对话都重述一遍不现实，
写进 `AGENTS.md` 才能让 AI 在**每一次**改代码时都带着它们。

**为什么规则层不能代替任务层**：`AGENTS.md` 说的是"不许做什么"，
不告诉你"这次改哪、改到什么程度算完成"。没有任务层的范围与验收标准，
AI 的默认行为就是"顺手多改一点"，而这正是这个项目最贵的回归来源。

### 与其它工具的适配

- 本项目以 **`AGENTS.md`** 为唯一规则文件（通用 Agent 标准，Claude Code / Codex / Cursor 都能读）；
- 如果你用 Claude Code 且希望走 `CLAUDE.md`：**不要复制一份内容**，用一行引用即可，
  否则两份规则会漂移：
  ```markdown
  <!-- CLAUDE.md -->
  本项目的规则见 @AGENTS.md（唯一来源，不要在本文件里重复维护）。
  ```
- 如果你用 Cursor：`.cursorrules` 同样只写一句 `Follow AGENTS.md at the repo root.`。

## 二、开始之前：先建立基线（没有基线就没有"没改坏"）

**这是全部流程里最容易被跳过、也最贵的一步。**

```powershell
# 1. 工作区必须干净（有未提交改动就先提交/暂存，否则分不清谁改坏的）
git status --short

# 2. 记下当前测试与静态检查状态
$env:QT_QPA_PLATFORM="offscreen"; .venv\Scripts\python.exe -m pytest tests -q
.venv\Scripts\python.exe -m ruff check src tests

# 3. 如果要用"快照比对"证明行为不变（推荐，见第四节），先把快照存下来
$env:MODU_CHECK_DEPS="$env:TEMP\check_before.json"; .venv\Scripts\python.exe -m modu_workbench
```

三条基线里任何一条不干净，就先修它 —— **不要在一个红色的基线上开始重构**，
否则你永远说不清"这个失败是我引入的还是本来就有的"。

## 三、四个场景的提示词（复制后替换 `[方括号]` 里的内容）

### 场景一：单模块通用优化（格式 + 颗粒度 + 可测试 + 可复用）

适用：一个文件或一个模块的整体梳理。**要求 AI 先出方案、再改代码**，
避免直接产出一个无法逐行审查的大 diff。

````text
你正在优化本仓库的 [文件路径/模块名]，例如 src/modu_workbench/core/video/downloader.py。

【必读】先读仓库根目录的 AGENTS.md，它规定了架构红线、行为守恒铁律与验证命令。
        本任务的所有约束都以它为前提，不要再向我确认那些已经写在里面的内容。

【目标】在完全保持现有行为和公开接口不变的前提下：
1. 格式与规范：符合 AGENTS.md 的代码规范；命名统一、无冗余代码、注释写"为什么"。
2. 颗粒度最小化：把过长函数/方法拆成单一职责的小单元。参考阈值：
   - 单个函数 ≤ 40 行（Qt 的 `_build_ui`、纯数据表、QSS 字符串可例外，但要写明理由）
   - 单个文件 ≤ 500 行逻辑代码（不含注释与空行）
3. 可测试：把纯逻辑与 I/O（网络/文件/数据库/Qt）分离，让拆分出来的单元能被单元测试
   直接覆盖。新抽出的纯函数必须补 tests/ 下对应用例。
4. 可复用：识别可提取的工具函数，**优先复用 core/platform/ 与 ui_kit/components/ 里已有的**；
   跨板块重复的实现收敛到 core/platform（各板块只留签名与默认值的薄封装）；
   板块内部重复的收敛到该板块包内；绝不新建"万能 utils"。

【硬性约束】
- 不改变任何导出的函数/类/变量的名称与签名；不删 `__all__` 里的名字。
- 不改变条件分支的执行路径、异步 await 位置、副作用调用次数与顺序。
- 不新增依赖；不重排 import；不删 `# noqa: BLE001` 等意图注释。
- 不修改现有测试来让它们变绿。若某个测试确实绑定了被你改掉的实现细节，
  停下来告诉我"这是设计变更"，不要自行改写断言。
- 重构后 `pytest tests -q` 与 `ruff check src tests` 必须全绿。

【输出格式 · 第一步（先只输出这一步，等我确认）】
1. 现状诊断：这个模块的具体问题（带行号），按"格式/颗粒度/可测试/可复用"四类归；
2. 改造方案：改哪些点、为什么改、预计影响哪些文件与公开接口；
3. **行为守恒证明方案**：你打算怎么证明"只搬家、没改行为"？
   —— 例如"对外行为快照比对""整份输出 sha256 前后一致""现有 N 条用例覆盖了这些分支"；
4. 风险与回滚：哪一步最可能出问题、出问题时怎么退回去。

【输出格式 · 第二步（我确认后再做）】
- 按"一个最小可验证单元"分批改，每批改完立刻跑对应测试并报告结果；
- 最后给出：改动文件清单、公开接口 diff（应当为空）、测试与 ruff 的实际输出、
  以及 CHANGELOG 条目草稿。
````

### 场景二：样式优化（QSS / 组件外观）

适用：`ui_kit/theme*.py`、`ui_kit/tokens.py`、某个页面的局部 `setStyleSheet`。

本项目的特殊之处：**样式是字符串**，改错一个 `QWidget` 选择器可能让六个板块同时变样，
而且"看起来没坏"不等于没坏。所以要用 **QSS 全文哈希** 当裁判。

````text
你正在优化 [文件/组件] 的样式代码，目标是在**视觉表现完全不变**的前提下提升可维护性。

【优化维度】
1. 语义化：一律使用 ui_kit/tokens.py 的令牌（颜色/间距/圆角/阴影/字号），
   不允许硬编码十六进制色值或魔法数字。发现硬编码时，先确认令牌里有没有等价项；
   没有就**先问我**要不要新增令牌（新增令牌会影响所有板块）。
2. 结构：合并重复声明、删除无用规则、消除 !important 滥用、减少选择器嵌套深度。
3. 颗粒度：按控件族组织（本项目已分为 theme_qss_base/forms/views/boards/shell 五个模块）。
   不要新建全局样式文件，也不要把某个板块的专用样式塞进通用分组。
4. 状态完整性：hover / focus / disabled / checked / dark mode 等状态不得缺失或改变。

【硬性约束】
- 不修改任何 `setObjectName(...)` 的值、任何 QSS 选择器里的 objectName / 类名。
- 不改变现有视觉表现：颜色、间距、字体、布局、断点行为**逐项不变**。
- 不引入新的样式框架/预处理器/图标库。
- Qt 的已知坑不要"顺手修"：下拉弹出层是独立窗口，圆角与选中色有专门注释说明为什么
  现在这么做（见 theme_qss_forms.py 的「弹出列表」段），改动前先读完那段注释。

【必须给出的证明】
- 改之前与改之后各跑一次：
  ```python
  from modu_workbench.ui_kit.theme import TOKENS, DARK, LIGHT, app_qss
  import hashlib
  for name, t in (("LIGHT", LIGHT), ("DARK", DARK)):
      qss = app_qss(t)
      print(name, len(qss), hashlib.sha256(qss.encode()).hexdigest()[:16])
  ```
  **纯搬家重构**必须两个哈希完全相同；如果哈希变了而你认为样式没变，
  必须逐字节解释差在哪（否则就是视觉变更，按视觉变更走评审）。
- `pytest tests/architecture/test_ui_design_system.py tests/smoke -q` 通过。

【输出格式】
先输出方案（改动点 + 受影响控件族清单 + 令牌增删清单），确认后再改；
改完附上前后 QSS 哈希与测试输出。
````

### 场景三：跨文件重构（搬代码，不改行为）

适用：把一段逻辑挪出原文件、拆分子模块、收敛重复实现。

这是最容易"改 A 坏 B"的场景。要害是三件事：**允许改哪些文件、哪些行为必须保留、
交付时拿什么证明**。所以要求 AI 先做影响面扫描。

````text
你正在对 [模块名/目录] 做跨文件重构。严格按下面流程执行，不要跳步。

【允许修改的文件】
- 新增：[新文件路径]（存放被抽出的逻辑）
- 修改：[文件 A]（改为引用新文件）、[文件 B]（同）
- 修改：[测试目录下新增用例]
禁止修改：[公共接口文件、配置、打包脚本、其它板块、数据库 schema]
（需要动到这里面的任何一项，先停下来问我。）

【必须保留的行为】
- 原有导入路径不变：调用方 `from [原模块] import [名字]` 必须照旧可用，
  必要时在原模块保留再导出（薄封装），不要逼下游改 import。
- 所有现有测试一行不改，重构后 100% 通过。
- 错误类型、日志位置、副作用调用顺序、用户可见文案保持不变。
- 打包相关：若新增模块被"字符串动态导入"，必须同步两个 spec 的 hiddenimports
  （有闸门 tests/architecture/test_dynamic_imports_bundled.py 会拦）。

【第一步：影响面扫描（必须先做，输出给我看）】
1. 目标函数/类/常量被哪些文件引用？分"直接 import""同模块调用""字符串/反射引用"三类列出，
   每条写清文件、行号、受影响原因、处置方式（不动 / 改 import / 保留再导出）。
2. 有没有测试直接引用它？（`grep -r "from .* import .*名字" tests/`）
3. 有没有架构闸门会因为这次移动而失败？（依赖边界、模块 `__all__`、启动预算、导入环）
4. 这次移动会不会改变**导入副作用顺序**（模块级创建单例、注册表填充、日志初始化）？

【第二步：分批实施】
- 一批只做"搬 + 引用"，不改逻辑；搬完立刻 `pytest tests -q`；
- 每一批给出：改了哪些文件、公开接口 diff（应为空）、测试结果。

【第三步：证明】
- 对"纯搬家"的部分给出可机器验证的证据：行为快照/哈希/注册表清单前后一致；
- 列出仍需人眼确认的点（如果有）。
````

### 场景四：代码审查（让 AI 先审再改）

适用：动一个核心文件之前，先花 10 分钟让 AI 当"严苛审查者"。
比"优化一下"有效得多，因为审查可以只输出结论、不产出 diff。

````text
Role: 你是一名以严苛著称的 Python / PySide6 桌面端资深工程师，负责生产级代码审查。
      本仓库的规则见根目录 AGENTS.md（分层、行为守恒、异常处理、测试规范）。
Task: 审查 [文件/模块]，按下面六个维度逐一检查：
      1. 格式与规范（是否遵守 AGENTS.md）
      2. 颗粒度（长函数、长文件、职责混杂）
      3. 可测试性（纯逻辑与 I/O 是否分离、有没有非测不可的隐藏依赖）
      4. 可复用性（与 core/platform、ui_kit/components 的重复实现；跨板块重复）
      5. 对周边模块的影响（隐式副作用、跨模块耦合、导入顺序敏感处）
      6. 样式/资源质量（硬编码色值、objectName 滥用、未用样式）
Constraints:
- 直言不讳指出问题，**不要先夸再挑毛病**。
- 每个问题必须给出：位置（文件:行号）、风险等级（P0 致命 / P1 严重 / P2 一般 / P3 建议）、
  具体修改方案（可运行代码，不要伪代码）。
- 特别扫描：`except Exception: pass`（本项目禁止）、未收窄的宽捕获、
  跨板块 import（架构违规）、可变默认参数、Qt 对象生命周期（父子关系/信号重复连接）、
  阻塞式 I/O 出现在 UI 线程、以及"实现了但没接界面入口"的新死代码。
- 如果某处不需要改，**明确说"无需修改"**，不要为了凑数强行提建议。
Format:
1. 问题清单（按 P0→P3 排序，一行一条，只写位置 + 一句话结论）
2. 逐条分析与修改方案（含代码）
3. 修改优先级与建议的执行顺序（哪几条必须一起改、哪几条可以单独上）
````

## 四、怎么证明"行为没变"（本仓库的三种硬证据）

提示词里的"行为不变"是软约束，**下面这些才是硬证据**。挑一个和改动性质匹配的用。

### 1. 现有测试（默认，最优先）

```powershell
$env:QT_QPA_PLATFORM="offscreen"; .venv\Scripts\python.exe -m pytest tests -q
```

`tests/architecture/` 那 14 个文件本身就是"设计没被破坏"的断言集合：
依赖边界、导入无环、动态导入已打包、启动预算、`__all__` 可解析、版本单一来源、
设计系统尺度、页面约定。**重构让它们变红 = 设计被破坏，不是"测试太严"。**

### 2. 输出快照比对（适合"结果是一坨数据/字符串"的重构）

- **打包自检**（`app/selfcheck.py`，17 项，覆盖渲染/转换/播放/各板块内核/打包资源）：

  ```powershell
  $env:MODU_CHECK_DEPS="$env:TEMP\check_before.json"; .venv\Scripts\python.exe -m modu_workbench
  # …重构…
  $env:MODU_CHECK_DEPS="$env:TEMP\check_after.json";  .venv\Scripts\python.exe -m modu_workbench
  # 逐项与顺序都必须一致
  ```

- **整份 QSS**：`sha256(app_qss(ThemeTokens()))` 前后一致（见场景二）。
- **注册表类数据**：把 `TOOL_REGISTRY` / `TOOL_ORDER` / `TOOL_CATEGORIES` 序列化成
  JSON 前后比对（`core/document/tools.py` 这类"注册即行为"的模块适用）。

这类快照的价值在于：它不依赖"我想得到哪些分支"，而是**整份输出逐字节**比对。

### 3. 结构不变量（适合"拆分"类重构）

拆分只应该改变"代码住在哪"，不应该改变"有什么"。可机器检查的不变量：

- `__all__` 集合不变；`grep` 公共名字的引用点数量不变；
- 函数签名（参数名、默认值、返回注解）不变 —— 可以用 `inspect.signature` 批量比对；
- 类的方法集合不变（`dir()` 差集为空）；QSS/`setObjectName` 字面量集合不变。

### 4. 界面结构探针（拆 Qt `__init__` / `_build_ui` 时**必须**做）

这是本仓库最容易被"测试全绿"骗过去的地方：把一个 `__init__` 拆成 `_build_*` 时，
只要多写一次 `QVBoxLayout(self)`，第二份 layout 就会变成**孤儿布局** ——
控件全挂在它上面，界面上直接少一半，而所有用例仍然通过，只在控制台留一行
`QLayout: Attempting to add QLayout ... which already has a layout`。

做法（十行代码，`docs/OPTIMIZATION_REPORT.md` 单元 8 就是这么抓到的）：

```python
# 1) 把目标文件切到 HEAD 版本，构造同一批页面，导出结构指纹
# 2) 切回工作区版本，再导一次
# 3) 逐字段比对
import json
from PySide6.QtWidgets import QApplication, QWidget
app = QApplication([])
page = SomePage()
print("JSON" + json.dumps({
    "widgets": len(page.findChildren(QWidget)),
    "layout_items": page.layout().count() if page.layout() else None,
    "attrs": sorted(a for a in vars(page) if a.startswith("_") and not a.startswith("__")),
    "texts": [w.text() for w in page.findChildren(QWidget) if hasattr(w, "text") and w.text()],
    "placeholders": [w.placeholderText() for w in page.findChildren(QWidget)
                     if hasattr(w, "placeholderText") and w.placeholderText()],
}, ensure_ascii=True, sort_keys=True))
```

三条注意：

- **切文件前后一定要 `try/finally` 还原**，否则探针一失败工作区就停在 HEAD 版本上；
- `findChildren(QWidget)` 比 `findChildren(object)` 更能反映"用户能看到的控件"
  （后者会把 layout 也算进去，数字对不上）；
- `ensure_ascii=True`：Windows 中文控制台是 GBK，直接打印 emoji/中文会
  `UnicodeEncodeError`，探针会"莫名其妙"失败。

## 五、执行纪律（这几条比提示词本身更重要）

1. **一次只改一个最小可验证单元。** 每一步应能在 5–10 分钟内完成，能独立跑通测试。
   "顺手把隔壁也优化了"是回归的头号来源。
2. **先方案后代码。** 直接要完整重构代码，diff 往往大到无法逐行审查；
   先审方案能把问题拦在生成之前（场景一/二/三都强制了这一步）。
3. **测试是裁判，不是障碍。** 测试红了先判断"是代码错了还是设计变了"。
   前者改代码，后者要显式说明并记 CHANGELOG —— 绝不改断言让它变绿。
4. **不要在没有测试的模块上做大重构。** 先补测试（哪怕只是把它的输出快照下来），再动手。
5. **规则文件和任务提示词分工。** 长期规范进 `AGENTS.md`；本次目标进对话。
   任务结束后，如果发现某条约束"以后每次都要交代"，把它**提升**进 `AGENTS.md`。

   相关 `docs/` 同步、`MODU_CHECK_DEPS` 自检 17 项全 true。

## 六、这个仓库的推荐起步顺序

不要一上来就动 `core/document/sheet.py`（1719 行）或 `boards/gallery/board.py`（1527 行）。
按"风险从低到高、收益从确定到不确定"排：

| 顺序 | 目标 | 为什么从这里开始 | 现成工具 |
|---|---|---|---|
| 1 | 板块内重复实现（同一 `_busy/_report/_idle` 抄多份） | 纯搬家、无算法风险，能被"方法集合不变 + 板块 UI 用例"双重验证 | 场景三 |
| 2 | 跨板块重复实现（`safe_filename`/`unique_path`） | 收敛到 `core/platform`，架构闸门天然支持 | 场景三 |
| 3 | 巨型"装配/注册"函数（`selfcheck.run_checks`、`tools._register_all`） | 内容是一串平铺步骤，拆开不会碰到业务分支 | 场景一 + 快照 |
| 4 | 巨型字符串（`theme.app_qss` 714 行） | 只能"搬"，不能"改"，哈希一比就知道有没有动到样式 | 场景二 |
| 5 | 板块 UI `__init__` / `_build_ui`（150~260 行） | 只做"分节 + 抽方法"，不碰信号连接顺序 | 场景一（分批） |
| 6 | 领域算法文件（`sheet.py` 公式引擎、`parser.py`、`writer.py`、`downloader.py`） | 逻辑密度最高、测试最细，**必须**先补测试再动 | 场景四 → 场景三 |

**第 6 档的特别提醒**：`core/document/sheet.py` 的公式解析器有一个"每次求值前保存、
结束后恢复 token 流"的约定（`docs/ARCHITECTURE.md`「墨软文档设计要点」），
把它拆成多个函数时，**状态保存/恢复的边界不能跟着函数边界走**，否则会出现
"单元格里再嵌公式就报缺少 )"——这类 bug 只有特定的嵌套公式才触发，
常规用例全绿。动它之前先把嵌套公式的用例补齐。
